01

JSX & components

A React app is a tree of components. A component is a JavaScript function that returns a description of some UI.

Components

A component is a function that returns UI

  • It's a normal JavaScript function.
  • Its name starts with a capital letter: Greeting, not greeting.
  • It returns JSX: HTML-looking syntax that describes what to show.
  • You use it like a tag, <Greeting />, as many times as you want.
  • Every example here has an App component. That's what the Preview shows.

Under the hood · press → to follow it

JSX is not HTML. It's JavaScript that describes HTML.

Every box above was produced live in this page by Babel and React. Click { } Compiled on any example to see its compiled version.

JSX rules

The 6 rules of JSX

  1. One parent element. Use a Fragment <>…</> if you don't want an extra div.
  2. className, not class. htmlFor, not for. (class and for are JavaScript words.)
  3. Close every tag: <input />, <br />.
  4. { } opens a window into JavaScript: variables, math, function calls, ternaries.
  5. camelCase: onClick, tabIndex. style takes an object: style={{ color: 'red' }}.
  6. Capital letter = your component. lowercase = HTML tag.

Props

Props: the arguments of a component

  • Pass them like HTML attributes: <ProfileCard name="Sara" />. Use { } for anything that isn't a string.
  • Receive them as one object. We usually destructure it: function ProfileCard({ name, role }).
  • Default values work like normal JS: { online = false }.
  • Whatever is between the tags arrives as children.
  • Props are read-only. A component never changes its own props (see the 🐞 tab).

The component tree

Data flows down the tree as props

Conditions

Showing things conditionally: it's just JavaScript

  • Early return: if (!loggedIn) return <Login />;
  • Ternary, for this or that: {ok ? <A /> : <B />}
  • &&, for this or nothing: {isNew && <Badge />}
  • ⚠ {count && …} prints 0 when count is 0. That's Bug 9. Use count > 0 &&.
  • null, false and undefined render nothing.

Lists

Lists: .map() data to JSX, and give each item a key

  • There's no special loop syntax. Use the array methods from the JS sessions: map, filter.
  • Each item needs a key: a stable, unique id that tells React which item is which between renders.
  • Without it, React warns in the console (🐞 tab). With the index as key, reordering mixes items up. That's Bug 7.
  • Keys come from your data (a database id). Not from Math.random(), and not the index if the list can change.

02

State & events

Props come from outside. State is a component's own memory. When state changes, React renders again.

Events

Events: pass a function. Don't call it.

  • onClick={handleClick} passes the function. React calls it later, on click.
  • onClick={handleClick()} calls it now, during render, and passes its return value (🐞 tab).
  • Need an argument? Wrap it in an arrow: onClick={() => greet('Sara')}.
  • Same idea as the this session: handing over a function is not the same as calling it.

State

Why can't I just use a normal variable?

  • Click +1 on the 🐞 tab. The console counts up, but the screen stays at 0.
  • ❶ Changing a local variable doesn't tell React to render again.
  • ❷ Even if it did render, let count = 0 runs again and starts from zero. Local variables don't survive between renders.
  • useState solves both: React keeps the value for you, and the setter triggers a render.

Anatomy

useState piece by piece

const [count, setCount] = useState(0);
count

The value for this render. Read it, but never assign to it.

setCount

“Please render again with this new value.” The change shows up on the next render.

0

The starting value. Used on the first render only, then ignored.

The [a, b] is array destructuring, from the JS sessions. You choose the names: [user, setUser], [isOpen, setIsOpen].

How React updates the screen

Trigger → Render → Commit

See it happen

“Rendering” just means React calls your function again

  • Click +1 and watch the console: App() runs again, top to bottom.
  • Each run sees a new value of count and returns new JSX.
  • The dashed boxes are a helper for this course, <RenderBox>. They flash and count every time they render. You'll see them again in Part 5.
  • So code in a component body runs on every render. That's why it must be fast and have no side effects.

The most surprising rule

State is a snapshot: it doesn't change while your code runs

Try it

“+3” adds 1, and the log shows the old value

  • Inside one render, count is a constant. It was 0 when the click happened, so every line says “set it to 0 + 1”.
  • console.log(count) right after setCount shows the old value. The new value only exists in the next render.
  • When the new state depends on the old one, pass an updater function: setCount(c => c + 1).

Lifting state up

Data down, events up

Lifting state up

Two components need the same state? Move it to their parent.

  • 🐞 tab: each panel has its own isOpen, so both can be open at once.
  • ✅ tab: the parent owns one openIndex and passes isOpen down as a prop…
  • …plus a function, onShow, that a child calls to ask the parent to change it.
  • One source of truth. The children are “controlled” by their parent.

Forms

Controlled inputs: state is the single source of truth

  • value={name}: the input shows the state.
  • onChange: every keystroke updates the state, then React renders the new value.
  • Checkboxes use checked and e.target.checked.
  • Because the values live in state, you can show them, validate them, or disable the button as the user types.
  • On submit, e.preventDefault() stops the browser from reloading the page. Forgetting it is Bug 13.

03

Effects & refs

Rendering must be pure. Anything that reaches outside React (timers, network, the document) goes in an effect.

Two kinds of code

Rendering is a recipe. Effects are deliveries.

🎨 Render: must be pure

Same props + state → same JSX. Every time. No surprises.

  • Calculate, filter, format, return JSX ✅
  • No fetch, no timers, no document.title = … ❌
  • No changing variables outside the component ❌

⚡ Side effects: talk to the outside world

  • In event handlers, when caused by a user action: onClick={save}. This is the best place for most of them.
  • In useEffect, when caused by being on screen: connect to a chat, start a timer, sync with a non-React widget, fetch data for what's shown.

Ask: “Does this happen because the user did something, or because the component is showing?” Did something → event handler. Showing → effect.

Anatomy

useEffect piece by piece

useEffect(() => { const conn = connect(roomId); return () => conn.disconnect(); }, [roomId]);
Effect

Runs after React has updated the screen. Never during render.

Cleanup (optional)

Undoes the effect. Runs before the next effect and when the component is removed.

Dependencies

When to run again. [roomId] means whenever roomId changed. [] means only once. No array means after every render.

Live: a real component reports what React does

When do effects and cleanups run?

Try each dependency setting. Press the buttons and read the log on the right.

Cleanup

Start something in an effect? Stop it in the cleanup.

  • The clock starts a timer when it appears.
  • Click Hide clock: React runs the cleanup, and the timer stops (🧹 in the console).
  • Without the cleanup, the timer keeps running forever, even with no clock on screen. That's Bug 5.
  • Every subscription has an opposite: addEventListener / remove…, setInterval / clearInterval, connect / disconnect.

“Why does my effect run twice?!”

StrictMode mounts → unmounts → mounts again, on purpose

  • This example runs inside <StrictMode>, like a new Vite or Next.js app.
  • In development only, React runs every effect, its cleanup, then the effect again. Look at the first 3 console lines.
  • Why? If your cleanup is right, the user can't tell the difference. If it's missing, you'll see two connections. It's a bug detector.
  • Don't “fix” it by removing StrictMode or adding a flag. Fix the cleanup.

Data fetching

Fetching: loading, error, data, and ignoring stale answers

  • Three states to handle: loading, error, data. Users will see all three.
  • The effect depends on [userId], so it fetches again whenever the user changes.
  • The ignore flag: if the user switches before the answer arrives, the cleanup marks the old request as stale (Bug 12 shows why).
  • Try User 4 for the error state. fakeApi is a pretend server with a delay, built into this deck.
  • In real projects: fetch() works the same way, but most teams use TanStack Query or their framework's data loading.

Refs

useRef: a box React keeps for you, but never watches

  • const ref = useRef(start) gives you { current: start }. It is the same object on every render.
  • Use 1: DOM elements. <input ref={inputRef} />, then inputRef.current.focus().
  • Use 2: values that must survive renders but don't affect the screen: interval ids, previous values.
  • Changing ref.current does not re-render. If it should show on screen, it's state, not a ref (tab 2).
  • Don't read or write refs during render. Use them in handlers and effects.

The most common over-use

You might not need an effect

  • Can you calculate it from props or state? Then do it during render. No state, no effect.
  • Look at the console on the 🐞 tab: two renders per keystroke, and the first one shows stale results.
  • Logic caused by a click? Put it in the click handler, not in an effect that “watches” state.
  • Expensive calculation? useMemo (Part 5). Still no effect.
04

Sharing state & logic

Context to skip the middlemen. Reducers for complex updates. Custom hooks to reuse logic. And the two rules every hook follows.

The problem and the fix

Prop drilling vs context

Context

Context: createContext → Provider → useContext

  1. createContext(default), once, outside components.
  2. Wrap a part of the tree in <ThemeContext.Provider value={…}>.
  3. Any component inside reads it with useContext(ThemeContext), however deep.
  4. When the value changes, every component that reads it re-renders.
  5. Good for: theme, current user, language. Not a replacement for all props: passing props is still the default.

Complex state

useReducer: describe what happened, decide the new state in one place

  1. Components dispatch actions: dispatch({ type: 'add', item }). They say what happened, not how to update.
  2. A reducer is a pure function: (state, action) => newState. All the update logic lives there.
  3. Same immutability rules: return a new array or object.
  4. Use it when many handlers update the same state, or the next state depends on several fields. For a simple toggle, useState is fine.

Reusing logic

Custom hooks: your own useSomething

  • A custom hook is a function whose name starts with use and that calls other hooks.
  • It shares logic, not state: every component that calls useToggle() gets its own state.
  • Resize the browser window and watch useWindowWidth update.
  • Real-world examples: useLocalStorage, useDebounce, useOnlineStatus, useFetch.

Two rules

The rules of hooks, and why they exist

1. Only call hooks at the top level of a component. Never inside if, loops, nested functions, or after an early return.
2. Only call hooks from components or custom hooks (functions named useSomething).

Why? React doesn't know your variable names. It remembers hooks by call order: “1st hook, 2nd hook, 3rd hook…”. Skip one, and every hook after it gets the wrong state.

The ESLint plugin eslint-plugin-react-hooks catches this in your editor. Bug 11 shows the crash.

05

Rendering & performance

When does React re-render, when should you care, and the tools to skip work: memo, useMemo, useCallback.

Re-renders

A component re-renders when…

  1. Its own state changes.
  2. Its parent re-renders. All children render too, whether or not their props changed.
  3. A context it reads changes.
  4. Myth: “it re-renders because its props changed”. Props change because the parent rendered, and that is the real reason.
  5. Re-rendering is not slow by default. React only touches the DOM where the output changed.

Live

Click each button and watch which boxes flash

  • Click App state: App, Header and Counter all render. Header has no props at all!
  • Click Counter's own state: only Counter renders. State changes go down the tree, never up.
  • Tip: React DevTools → ⚙ → “Highlight updates when components render” shows the same in real apps.

Skipping renders

memo skips a child, if its props are the same

  • memo(Component) compares each prop with Object.is. All the same → skip.
  • 🐞 style={{ … }} or onSelect={() => …} written inline makes a new object or function every render, so they are never “the same” and memo is useless.
  • ✅ useMemo(() => value, deps) and useCallback(fn, deps) give back the same object or function until a dependency changes.
  • Same “same box or new box” idea as state (Part 2).

Expensive calculations

useMemo: don't redo slow work on every keystroke

  • 🐞 tab: type fast in the box. It lags, because slowSquare (150 ms) runs on every render, even though n didn't change.
  • ✅ tab: useMemo(() => slowSquare(n), [n]) only recalculates when n changes.
  • Measure first. Most components never need this. Optimizing too early makes code harder to read.
  • The React Compiler (React 19 era) adds this kind of memoization automatically.

Identity

State belongs to a position in the tree. key changes the identity.

  • 🐞 tab: type a note for Sara, then click Omar. The note is still there!
  • Same component, same position, so React keeps its state. Only the props changed.
  • ✅ <Notes key={person} />: a different key means a different component. React throws the old one away, along with its state.
  • That's also why keys in lists matter (Bug 7), and why you never define a component inside another one (Bug 8).

BUG 01

The list that won't update

Click Add eggs. The console says the array grew. The screen doesn't change.

Why it happens

  1. push and post.likes++ change the object that is already in state.
  2. setItems(items) passes React the same box. Object.is(old, new) is true.
  3. React decides nothing changed and skips the render. Your data and your screen are now out of sync.

Rule: treat state as read-only. Make a new copy with ..., map, filter.

BUG 02

Too many re-renders

The app crashes before you click anything: Too many re-renders. React limits the number of renders to prevent an infinite loop.

Why it happens

  1. onClick={setCount(count + 1)} calls setCount right now, while rendering.
  2. Setting state triggers a render… which calls setCount again… which triggers a render…
  3. React stops it after about 50 rounds and throws.

Rule: onClick wants a function. Give it () => setCount(count + 1). Never call setState directly in the component body.

BUG 03

Three likes, one counted

Click Like 3 times quickly. 1.5 s later you get ❤️ 1, not 3.

Why it happens

  1. All three clicks happen in the same render, where likes is 0.
  2. Each timer callback closes over that 0. They all say “set to 0 + 1”.
  3. It's the snapshot rule from Part 2, spread out over time.

Rule: new state depends on old state → setX(prev => …). Always safe, even later.

BUG 04

The timer stuck at 1

The screen shows 1s forever. The console keeps saying seconds = 0.

Why it happens

  1. With [], the effect runs once, in the first render, where seconds = 0.
  2. The interval callback is created then, so it remembers that 0 forever (a stale closure).
  3. Every tick sets it to 0 + 1. Stuck at 1.
  4. The deps array is a promise to React: “my effect only uses these values”. [] was a lie here.

Rule: list every value the effect reads in its deps (the linter does it for you), or use an updater so you don't need the value.

BUG 05

The ghost timer

Click Hide: the ticks continue. Click Show: now two tickers are running.

Why it happens

  1. React removes the component from the screen. It can't know about the interval you started.
  2. With no cleanup, the timer lives on: a memory leak. If it calls setState, it updates a component that's gone.
  3. Every mount adds another timer. StrictMode would show you this on the first load.

Rule: if the effect starts, subscribes or connects, return a cleanup that stops, unsubscribes or disconnects.

BUG 06

The endless fetch loop

The request counter in the console never stops climbing, about 3 requests a second, forever. Press ■ Stop.

Why it happens

  1. Every render creates a new options object. {} === {} is false.
  2. React sees a “changed” dependency → runs the effect → fetch → setPosts → render → new options → …
  3. In a real app: thousands of requests, a hot laptop, an angry backend team.

Rule: put primitives (strings, numbers) in deps. Create objects inside the effect, or useMemo them.

BUG 07

Notes on the wrong person

Type a note next to Sara, then click Add to top. Your note is now next to “New person”.

Why it happens

  1. React matches old and new items by key. Before: Sara was key 0.
  2. After adding to the top, “New person” is key 0. React thinks row 0 is the same row with a new name.
  3. So it keeps row 0's DOM, including the typed text in its input, and gives it to “New person”.

Rule: keys must identify the data, not the position. Index keys are only OK for lists that never reorder, insert or delete.

BUG 08

The input that loses focus

Type a word. After every letter the input loses focus and you have to click it again.

Why it happens

  1. Every render of App runs function SearchBox() {…} again and creates a brand-new function.
  2. To React, a new function means a different component type. Old SearchBox ≠ new SearchBox.
  3. So it destroys the old input and creates a new one on every keystroke. Focus and state are lost.

Rule: define components at the top level of the file. Pass what they need as props.

BUG 09

The mysterious 0

With no messages, the heading says “Inbox 0”. Where does the 0 come from?

Why it happens

  1. a && b returns a if a is falsy. So 0 && <Badge/> is 0.
  2. React skips false, null and undefined, but numbers are rendered, including 0.

Rule: make the left side a real boolean: count > 0 &&, !!count &&, or use a ternary.

BUG 10

Props copied into state

Click Omar. App knows the user changed, but the greeting still says Hello, Sara.

Why it happens

  1. useState(initial) uses initial once, on the first render. After that it's ignored.
  2. The prop changes, but the state copy doesn't. Now there are two sources of truth, and they disagree.
  3. If you really need an editable copy (a draft form), reset it with <Greeting key={user} />.

Rule: don't mirror props in state. Read the prop directly.

BUG 11

A hook inside an if

Click Toggle bio: Rendered more hooks than during the previous render.

Why it happens

  1. React remembers hooks by call order: render 1 called 1 useState.
  2. Render 2 calls 2. The count doesn't match, so React can't know which state is which.
  3. Same problem with hooks in loops, or after an early return.

Rule: call hooks at the top, unconditionally, every render. Put the if after the hooks.

BUG 12

Search shows the wrong results

Type ram quickly. You should get only Rami, but the list ends up with everything containing “r”.

Why it happens

  1. Each letter starts a request: “r”, “ra”, “ram”.
  2. Networks don't answer in order. Here, the shorter word is slower, so “r” answers last.
  3. The last answer to arrive wins, even though it's for an old query. Read the order in the console.

Rule: every fetch effect needs a cleanup that marks old requests as stale (or an AbortController). Libraries like TanStack Query do this for you.

BUG 13

The form that resets everything

Type an email and press Subscribe. “Thanks!” flashes, then the whole app starts over, empty.

Why it happens

  1. A <form> submit is a browser feature from before JavaScript apps: it sends the data and loads a new page.
  2. A reload throws away all JavaScript memory, React state included.
  3. This deck catches the reload and acts it out, so the slides survive. A real page would really reload.

Rule: handling a form in React? First line: e.preventDefault(). (React 19 form Actions do this for you.)

BUG 14

Uncontrolled → controlled

Type one letter. A warning appears: A component is changing an uncontrolled input to be controlled.

Why it happens

  1. value={undefined} means “no value”, so the input manages itself (uncontrolled).
  2. After the first letter, value="S", so React suddenly controls it. Switching modes mid-life is unpredictable.
  3. Same thing happens with data from an API that isn't loaded yet: value={user.name}.

Rule: controlled inputs always get a string: useState(''), or value={x ?? ''}.

When React “doesn't work”

The React debugging checklist

  1. Read the console. React's warnings name the bug: keys, controlled inputs, hooks order, max update depth.
  2. Screen not updating? Did you call the setter? Did you mutate instead of copying (Bug 1)?
  3. Old value? It's a snapshot or a stale closure: use an updater, or fix the deps (Bugs 3 and 4).
  4. Runs too often? A new object or function in the deps (Bug 6), or a setter called during render (Bug 2).
  5. State lost or stuck? Think identity: keys, position in the tree, components defined inside components (Bugs 7, 8, 10).
  6. Use the tools: console.log in render, React DevTools (Components tab, highlight updates), StrictMode, eslint-plugin-react-hooks.
