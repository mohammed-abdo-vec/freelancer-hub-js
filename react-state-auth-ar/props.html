ما هي الـ Props؟

مراجعة سريعة: الـ props هي الطريقة التي يكلّم بها الأب أبناءه.

الفكرة

الكومبوننت دالة، والـ props هي مدخلاتها

  • الـ props مثل مدخلات الدالة (arguments): الأب يقرّرها، والابن يستقبلها.
  • هي للقراءة فقط. الابن لا يغيّرها أبدًا. إذا أراد تغيير شيء، يطلب ذلك من الأب.
  • يمكن تمرير أي قيمة: نص، رقم، object، مصفوفة، دالة، وحتى JSX (children).
  • كل مرة يعمل الأب رندر، يستدعي React دالة الابن من جديد مع props جديدة. تذكّروا هذه الجملة، هي مفتاح العرض كله.

متى يعيد الكومبوننت الرندر؟

قبل أن نقارن الـ props بـ Zustand، لازم نعرف بالضبط ما الذي يجعل كومبوننت يعيد الرندر (re-render).

ثلاثة أسباب فقط

لماذا عمل هذا الكومبوننت رندر؟

  1. تغيّرت الـ state الخاصة به (useState / useReducer / store).
  2. الأب عمل رندر. وافتراضيًا يعيد React رندر كل الأبناء، تغيّرت الـ props أو لم تتغير.
  3. تغيّرت قيمة context يقرأه بـ useContext.

خرافة مشهورة عن الـ props

❌ خرافة

"الكومبوننت يعيد الرندر لأن الـ props تغيّرت."

إذن (حسب الخرافة) الكومبوننت الذي لا يستقبل props لن يعيد الرندر أبدًا، والذي يستقبل نفس القيم لن يعيد الرندر.

←

✅ الحقيقة

"الكومبوننت يعيد الرندر لأن أباه عمل رندر."

React لا يقارن الـ props افتراضيًا. الأب عمل رندر ← استدعى كل أبنائه من جديد، حتى الابن الذي بلا props أصلًا.

الـ props لا تُطلق الرندر. هي فقط "تركب" مع رندر الأب.المقارنة بين الـ props القديمة والجديدة تحدث فقط إذا طلبناها بـ React.memo (الجزء ٦).

جرّب

اضغط كل زر وراقب أي صندوق يومض

  • RenderBox صندوق يومض ويعدّ كل مرة يعمل فيها الكومبوننت الذي يحتويه رندر. أول رقم 1 هو رندر البداية (mount).
  • اضغط App +1 ثلاث مرات: كل الصناديق تصير 4. حتى Header الذي لا يستقبل أي props!
  • اضغط Counter +1: فقط Counter يزيد. الـ state تؤثر على صاحبها وما تحته، ولا تصعد للأعلى.
  • سؤال: لماذا Display يعيد الرندر؟ ليس لأن count تغيّر، بل لأن App عمل رندر.

نفس التطبيق مع Zustand

ماذا لو عاشت الـ state خارج شجرة React تمامًا؟

تذكير سريع

Zustand في دقيقة

  • الـ store متغير خارج شجرة React. لا يوجد أب يملكه.
  • كل كومبوننت يشترك بنفسه عبر selector: (s) => s.user.
  • عند كل تغيير، Zustand يشغّل الـ selector لكل مشترك ويقارن الناتج بالقديم (Object.is). تغيّر؟ رندر. لم يتغير؟ لا شيء.
  • في الأمثلة الحية، create نسخة مصغّرة من Zustand (~٢٠ سطرًا فوق useSyncExternalStore) وتتصرف مثله تمامًا. في مشروع حقيقي: import { create } from 'zustand'.

نفس الشجرة، لكن الـ state في store

  • لا props بين الطبقات. Avatar يقرأ user مباشرة من الـ store.
  • اضغط Rename: يومض Avatar وحده. بعد ٥ ضغطات: Avatar عدّاده 6 وكل الباقي 1.

Context في المنتصف

React عنده حل مدمج للـ prop drilling. هل يحل مشكلة الرندر أيضًا؟ نصف الحل.

Context

Context يلغي الـ drilling، لكن لا يعرف الـ selectors

  • ✅ لا تمرير عبر الطبقات: أي كومبوننت تحت الـ Provider يقرأ القيمة مباشرة.
  • ✅ الطبقات الوسطى لا تعيد الرندر، بشرط أن يستقبل الـ Provider الشجرة كـ children (سنرى السبب في الجزء ٦).
  • ❌ عندما تتغير الـ value، كل من يستدعي useContext(UserCtx) يعيد الرندر، حتى لو كان يستخدم جزءًا لم يتغير.
  • ❌ لا يوجد selector في Context. القيمة كلها أو لا شيء.
  • لذلك Context ممتاز للقيم التي نادرًا ما تتغير: الثيم، اللغة، المستخدم المسجّل.

جرّب

ThemeBadge لا يهتم بالاسم… فهل يعيد الرندر؟

  • Context: اضغط Rename ٣ مرات: Avatar و ThemeBadge و RenameButton عدّادها 4. أما App و Layout فيبقيان 1.
  • ThemeBadge يقرأ theme فقط، و theme لم يتغير، ومع ذلك يعيد الرندر: كل مستهلك للـ context يعيد الرندر.
  • Zustand: نفس الضغطات: Avatar عدّاده 4 وكل الباقي 1. كل كومبوننت اختار بالـ selector الجزء الذي يهمه.

حلول بدون مكتبة

قبل أن تثبّت Zustand: ثلاث أدوات من React نفسه تقلّل الرندرات غير الضرورية.

الحل ١ · Colocation

ضع الـ state بجانب من يستخدمها

  • 🐞 open لا يحتاجها إلا Menu، لكنها في App. اضغط ☰ ٣ مرات: كل الصناديق 4.
  • ✅ أنزلناها داخل Menu. نفس الضغطات: Menu عدّاده 4، و App و Feed يبقيان 1.
  • القاعدة: ارفع الـ state فقط إلى أقرب أب مشترك، وليس أعلى من ذلك. أبسط وأسرع حل، وبدون أي مكتبة.

الحل ٢ · Composition

مرّر الكومبوننت كـ children بدل أن تنشئه في الداخل

  • 🐞 ThemeFrame عنده state، و <Feed /> مكتوب داخله. اضغط 🌓 ٣ مرات: ThemeFrame و Feed عدّادها 4.
  • ✅ App هو من ينشئ <Feed /> ويعطيه لـ ThemeFrame كـ children. نفس الضغطات: ThemeFrame عدّاده 4 و Feed عدّاده 1.
  • لماذا؟ الـ children عنصر صنعه App، و App لم يعمل رندر، فهو نفس العنصر تمامًا. React يرى أنه لم يتغير فيتخطاه.
  • هذا بالضبط ما يجعل UserProvider في الجزء ٥ لا يعيد رندر Layout.

الحل ٣ · memo

memo يقارن الـ props… ويخدعه أي object جديد

  • ١ 🐞 بدون memo: اضغط Like ٣ مرات ← Avatar عدّاده 4 رغم أن name لم يتغير.
  • ٢ ✅ memo(Avatar): يقارن كل prop بـ Object.is. كلها نفسها؟ يتخطى ← Avatar عدّاده 1.
  • ٣ 🐞 الفخ: style={{…}} و () => … تُنشأ من جديد في كل رندر، فلا تكون "نفسها" أبدًا ← Avatar عدّاده 4 مرة أخرى.
  • ٤ ✅ useMemo و useCallback يرجعان نفس الـ object والدالة حتى تتغير الـ deps ← Avatar عدّاده 1.
  • ملاحظة: App نفسه يعيد الرندر في كل الحالات. memo يحمي الابن فقط.
٧

أخطاء Zustand الشائعة

Zustand يقلّل الرندرات فقط إذا استخدمنا الـ selector بشكل صحيح. خطآن نراهما كثيرًا.

خطأ ١

useApp() بدون selector = اشتراك في كل شيء

  • 🐞 Avatar يحتاج name فقط، لكنه كتب useApp(). اضغط Notify ٣ مرات: Avatar عدّاده 4 رغم أن الاسم لم يتغير.
  • بدون selector، الناتج هو الـ state كلها، وهي object جديد مع كل set. إذن: "تغيّر" ← رندر.
  • ✅ useApp((s) => s.name): نفس الضغطات، Avatar عدّاده 1 و Bell عدّاده 4.
  • الـ destructuring لا يساعد: const { name } = useApp() ما زال يشترك في الكل.

خطأ ٢

selector يرجع { } جديدًا ← حلقة لا نهائية

  • 🐞 (s) => ({ name: s.name, unread: s.unread }) يصنع object جديدًا في كل مرة يُستدعى فيها.
  • Zustand يقارن بـ Object.is: الجديد ≠ القديم دائمًا ← "تغيّر!" ← رندر ← object جديد ← … حتى يوقفها React بخطأ Maximum update depth exceeded وينهار التطبيق (انظر الكونسول).
  • ✅ الحل الأبسط: selector منفصل لكل قيمة. كل واحد يرجع قيمة بسيطة تُقارن بشكل صحيح.
  • ✅ أو useShallow من Zustand (الشريحة التالية).

الحل في مشروع حقيقي

ثلاث طرق لقراءة أكثر من قيمة

  • useShallow يقارن محتوى الـ object (مفتاحًا مفتاحًا) بدل المرجع. نفس القيم؟ يرجع الـ object القديم نفسه ← لا رندر.
  • في Zustand v4 كان الخطأ ٢ يسبّب رندرات زائدة فقط. في v5 صار حلقة لا نهائية، لأنه يستخدم useSyncExternalStore مثل نسختنا المصغّرة.
  • القاعدة: الـ selector يرجع قيمة موجودة في الـ store، لا قيمة جديدة يصنعها.

الملخّص

من يعيد الرندر عندما تتغير القيمة؟

الطريقةأين تعيش الـ state؟من يعيد الرندر؟متى نستخدمها؟
Propsفي أقرب أب مشتركصاحب الـ state وكل الشجرة تحته، حتى من لا يستخدمهاالافتراضي. بيانات بين أب وأبناء قريبين
Contextفي Providerكل من يقرأ الـ context، حتى لو استخدم جزءًا لم يتغيرقيم نادرًا ما تتغير: الثيم، اللغة، المستخدم المسجّل
Zustandخارج Reactفقط من تغيّر ناتج الـ selector الخاص بهstate مشتركة بين أماكن بعيدة، أو تتغير كثيرًا
memo(أداة إضافية)يتخطى الابن إذا كانت كل الـ props نفسها (Object.is)كومبوننت ثقيل، مع useMemo / useCallback
الـ props لا تسبّب الرندر بنفسها. المشكلة أن الـ state المشتركة مع الـ props يجب أن تعيش عاليًا، ورندر الأب يجرّ كل ما تحته.

كلمة صريحة

لا تخافوا من الرندر

  • الرندر = استدعاء دوال JavaScript. React يقارن الناتج ويغيّر في الـ DOM فقط ما تغيّر فعلًا.
  • في أغلب التطبيقات، الرندرات "الزائدة" رخيصة جدًا ولن يلاحظها أحد.
  • تصبح مشكلة عندما: الشجرة كبيرة، أو التحديث متكرر (كتابة، سحب، مؤقت)، أو كومبوننت ثقيل (قائمة طويلة، رسم بياني).
  • قِس قبل أن تحسّن: React DevTools ← Profiler، وفعّل خيار Highlight updates لترى الوميض مثل RenderBox.

ترتيب الأدوات

  1. ابدأ بـ الـ props. هي الطريقة الطبيعية والأوضح.
  2. أنزِل الـ state أو مرّر children إذا رأيت رندرات زائدة.
  3. Context للقيم العامة التي نادرًا ما تتغير.
  4. Store مثل Zustand للـ state المشتركة بين أماكن بعيدة أو المتغيرة كثيرًا.
  5. memo لكومبوننت ثقيل، بعد أن تقيس.

الخلاصة في جملتين

الكومبوننت يعيد الرندر لأن أباه عمل رندر، لا لأن الـ props تغيّرت.

مع الـ props تعيش الـ state عاليًا فتعيد الشجرة كلها الرندر. مع Zustand تعيش خارج الشجرة، فيعيد الرندر فقط من اشترك بـ selector تغيّر ناتجه.
