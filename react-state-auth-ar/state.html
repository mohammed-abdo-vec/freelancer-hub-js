ما هو الـ State؟

بيانات تتغير مع الوقت، وعندما تتغير يجب أن تتغير الشاشة معها.

جرّب

لماذا لا يكفي متغير let عادي؟

  • في تبويب ❌ let اضغط أضف 1 عدة مرات: الكونسول يعدّ 1، 2، 3… لكن الشاشة تبقى 0.
  • السبب: React لا يعرف أن المتغير تغيّر، فلا يعيد الرندر.
  • ولو حصل رندر لأي سبب، فالسطر let count = 0 يعمل من جديد ويرجع الصفر.
  • في تبويب ✅ useState: React يحفظ القيمة بين الرندرات، وsetCount تطلب رندر جديد.
  • لاحظ أن الكونسول في ✅ يطبع القيمة القديمة. سنفهم السبب بعد قليل.

الفكرة الأساسية

🧠 الـ state = ذاكرة

قيمة يحفظها React للكومبوننت بين الرندرات. المتغيرات العادية تُنسى بعد كل رندر.

🔁 الكومبوننت = دالة

في كل رندر يستدعي React الدالة App() من جديد، وهي ترجع JSX يصف الشاشة الآن.

📣 setState = طلب

setCount(5) لا تغيّر الشاشة بنفسها. هي تقول لـ React: «القيمة تغيّرت، أعد الرندر».

نحن لا نغيّر الشاشة بأيدينا. نغيّر الـ state، وReact يرسم الشاشة من جديد.نفس الـ state يعطي دائمًا نفس الواجهة. لذلك سؤالنا في كل التطبيق: أين تعيش هذه القيمة؟

الرندر ≠ تحديث الـ DOM

«رندر» يعني فقط: React استدعى دالة الكومبوننت. تعديل الـ DOM يحدث في النهاية، وفقط إذا تغيّر شيء.

من يعيد الرندر؟

الكومبوننت صاحب الـ state، وكل أبنائه تحته افتراضيًا.

التفاصيل والأرقام في عرض الـ Props وإعادة الرندر.

نفس القيمة؟

إذا كانت القيمة الجديدة تساوي القديمة حسب Object.is، يتخطى React الرندر.

جرّب

الـ state لقطة ثابتة (snapshot) داخل كل رندر

  • اضغط أضف 3 في تبويب ❌: الرقم يزيد 1 فقط.
  • داخل هذا الرندر، count ثابت. الأسطر الثلاثة كلها تقول «اجعلها 0 + 1».
  • في تبويب ✅ نمرّر دالة: «خذ آخر قيمة وزد 1». React ينفّذها بالترتيب: 0←1←2←3.
  • لاحظ عدّاد الرندر: ثلاثة setCount = رندر واحد. React يجمع التحديثات (batching).

جرّب

المصفوفات والـ objects: انسخ، لا تعدّل (immutability)

  • في ❌ push اضغط «أضف خبز»: الكونسول يُظهر أن عدد العناصر يزيد، لكن الشاشة لا تتغير.
  • push يعدّل نفس المصفوفة. React يقارن بالمرجع: نفس المرجع = «لم يتغير شيء» = لا رندر.
  • الآن اضغط «رندر لسبب آخر»: يظهر الخبز فجأة! هذا النوع من الأخطاء صعب جدًا في المشاريع الحقيقية.
  • في ✅ spread ننشئ مصفوفة جديدة، فيرى React مرجعًا جديدًا ويعيد الرندر.

الخط المتقطع = اشتراك عبر selector، وليس props

  • لا يحتاج Provider. أي كومبوننت يستدعي الـ hook مباشرة.
  • كل كومبوننت يختار قطعته بـ selector، ويعيد الرندر فقط عندما تتغير هذه القطعة.
  • الـ store كائن JavaScript عادي: تقرأه وتعدّله حتى خارج React.
  • صغير جدًا (حوالي 1KB) وبدون كود إضافي كثير.
في مشروعك الحقيقي تثبّت المكتبة وتستورد منها: في هذا العرض، create نسخة من Zustand في حوالي 20 سطرًا، مبنية على useSyncExternalStore مثل الأصلية، وتعمل بنفس الطريقة تمامًا.

  • قواعد الـ immutability نفسها: [...s.items, item] وليس push.

ميزة مهمة

لماذا هذا مهم؟

الـ hooks تعمل فقط داخل كومبوننت. لكن الـ interceptor دالة عادية. getState() تعطيك آخر قيمة في أي مكان.

انتبه

getState() لا يشترك. لو استخدمته لعرض قيمة على الشاشة، لن تتحدث الشاشة. داخل الكومبوننت استخدم الـ hook مع selector.

مع Context هذا غير ممكن: قيمته موجودة داخل شجرة React فقط. تفاصيل التوكن في عرض الـ Auth.

الخلاصة

ما يجب أن تتذكره

  1. الـ state ذاكرة الكومبوننت. تغييرها بـ setX يطلب رندر جديد. المتغير العادي لا يفعل.
  2. الـ state لقطة ثابتة داخل كل رندر. إذا اعتمدت القيمة على السابقة: setX(prev => …).
  3. لا تعدّل مصفوفة أو object. أنشئ نسخة جديدة بـ ...spread وmap وfilter.
  4. أخوة يحتاجون نفس القيمة؟ ارفعها لأقرب أب مشترك.
  5. Context للقيم العامة النادرة التغير. ثبّت value بـ useMemo.
  6. Zustand للحالة العامة المتغيرة. دائمًا استخدم selector، وgetState() خارج React.
