Authentication (المصادقة)

"من أنت؟" تُثبت هويتك: إيميل وكلمة مرور، ثم توكن مع كل طلب.

مثل جواز السفر في المطار: يثبت أنك أنت.

إذا فشلت: 401 Unauthorized
"لا أعرفك. سجّل دخولك أو جدّد توكنك."

ثم

🎫

Authorization (الصلاحيات)

"هل مسموح لك؟" السيرفر يعرف من أنت، ويقرر هل دورك (role) يسمح بهذا.

مثل بطاقة الصعود: ليست كل البوابات لك.

إذا فشلت: 403 Forbidden
"أعرفك جيدًا، والجواب: لا."

في المشروع: طالب يفتح /admin فيحصل على 403 لأنه مسجّل لكن دوره student. أما زائر بدون توكن فيحصل على 401. الاسم الإنجليزي "Unauthorized" للـ 401 مضلّل قليلًا، فهو في الحقيقة يعني "غير مُصادَق".

stateless

السيرفر لا يتذكرك بين طلب وآخر

  • كل طلب HTTP مستقل تمامًا. السيرفر لا يعرف أن هذا الطلب جاء من نفس الشخص الذي سجّل الدخول قبل دقيقة.
  • لذلك يجب أن يحمل كل طلب دليلًا على هويتك: كوكي فيها رقم جلسة (session id)، أو توكن في الـ header.
  • تسجيل الدخول نفسه لا "يفتح" شيئًا على السيرفر. هو فقط يعطيك هذا الدليل لتستخدمه بعد ذلك.

الـ Auth في الفرونت إند = أين نحفظ الدليل، وكيف نرسله، وماذا نفعل عندما ينتهي.

طريقتان لإثبات الهوية

Session ID أم Token (JWT)؟

🍪 Session (stateful)🎟️ Token / JWT (stateless)
ماذا يأخذ المتصفح؟رقم عشوائي فقط sid=8f3a…توكن يحمل المعلومات بداخله { sub, role, exp }
أين بيانات الجلسة؟على السيرفر (ذاكرة أو قاعدة بيانات أو Redis)داخل التوكن نفسه، موقّعة بسرّ لا يعرفه إلا السيرفر
كيف يتحقق السيرفر؟يبحث عن الرقم في قاعدة البياناتيتحقق من التوقيع فقط، بدون قاعدة بيانات
كيف يُرسل؟كوكي، والمتصفح يرسلها تلقائيًاغالبًا header: Authorization: Bearer …
الإلغاء (logout)✅ سهل: نحذف الجلسة من السيرفر❌ صعب: التوكن صالح حتى ينتهي، لذلك نجعل عمره قصيرًا

المشروع يجمع الاثنين: access token قصير (JWT) لكل الطلبات، وrefresh token في كوكي، والسيرفر يحفظ رقمه (jti) حتى يستطيع إلغاءه.

السؤال الأشهر في الـ Auth

localStorage أم الذاكرة أم كوكي httpOnly؟

XSS = سكربت غريب يعمل داخل صفحتك (مكتبة مخترقة، input غير منظّف). CSRF = موقع آخر يجعل متصفحك يرسل طلبًا لموقعك مع كوكيزك.

🗄️ localStorage

  • ✅ يبقى بعد إعادة التحميل
  • ✅ سهل جدًا: سطر واحد
  • ❌ أي سكربت XSS يقرؤه ويرسله لنفسه
  • ❌ يبقى صالحًا عند المهاجم حتى ينتهي

لا يُرسل تلقائيًا، فلا CSRF، لكن خطر XSS أكبر.

🧠 الذاكرة (Zustand)

  • ✅ لا يُكتب في أي مكان يمكن سرقته لاحقًا
  • ✅ لا CSRF (لا يُرسل تلقائيًا)
  • ❌ يضيع عند إعادة التحميل
  • ⚠️ XSS ما زال يستطيع استخدامه أثناء فتح الصفحة

ممتاز للـ access token القصير.

🍪 كوكي httpOnly

  • ✅ JavaScript لا يستطيع قراءتها، فلا سرقة عبر XSS
  • ✅ تبقى بعد إعادة التحميل
  • ⚠️ تُرسل تلقائيًا، فتحتاج حماية CSRF: sameSite
  • ⚠️ لا نستطيع وضعها في header بأنفسنا

ممتازة للـ refresh token.

ماذا اختار المشروع؟

access في الذاكرة + refresh في كوكي httpOnly

الـ response interceptor: قلب التدفق كله

  • الشرط الأول: نتدخل فقط في 401. الـ 403 أو 500 ليست مشكلة توكن.
  • isAuthEndpoint: إذا فشل /auth/refresh نفسه بـ 401، لا نحاول refresh له!
  • _retry: علم نضعه على الطلب نفسه. إذا فشل بعد الإعادة، نستسلم.
  • http(original): يمر من جديد على الـ request interceptor، فيأخذ التوكن الجديد من الـ store.
  • فشل الـ refresh = الجلسة انتهت حقًا: نمسح الـ store والكاش، والـ guards تنقل المستخدم إلى /login.

جرّب · ٢

ثلاثة طلبات تفشل معًا: كم refresh؟

  • اضغط دخول، ثم ٣ طلبات معًا. نبدأ بتوكن منتهٍ عمدًا، فالثلاثة تحصل على 401.
  • serverRefresh يحاكي قاعدة السيرفر الحقيقي: كل كوكي تُستخدم مرة واحدة (rotation).
  • 🐞: ثلاث طلبات refresh بنفس الكوكي. الأول ينجح والباقي 401 ← خروج.
  • ✅: refreshPromise مشترك ← refresh واحد، والثلاثة تنجح.

ستة أخطاء تتكرر في المشاريع الحقيقية. لكل خطأ: ما المشكلة، وما الإصلاح.

أخطاء شائعة · ١–٣

التخزين، والخروج، والسباق

١. التوكن في localStorage

أي سكربت XSS يقرؤه ويرسله لنفسه.

الإصلاح: الذاكرة للـ access، والكوكي httpOnly للـ refresh.

٢. الخروج دون مسح الكاش

المستخدم التالي على نفس الجهاز يرى ملاحظات السابق للحظة.

الإصلاح: endSessionLocally() تمسح الـ store والكاش معًا.

٣. سباق الـ refresh

٣ طلبات تفشل معًا ← ٣ refresh، والـ rotation تقتل الجلسة.

الإصلاح: single-flight في refreshSession().

أخطاء شائعة · ٤–٦

الوميض، والثقة بالفرونت، والأسرار

٤. وميض صفحة الدخول عند reload

نبدأ بـ 'guest' فنحوّل إلى صفحة الدخول، ثم يصل التوكن فنرجع. وميض، وأحيانًا حلقة redirect.

الإصلاح: حالة ثالثة 'checking' و AuthBootstrap.

٥. الثقة بالـ role في الفرونت

إخفاء زر "Admin" ليس حماية. أي أحد يعدّل الـ JS أو يرسل الطلب بنفسه.

الإصلاح: الـ guard للتجربة، والسيرفر يرد بـ 401/403.

٦. أسرار داخل الـ JWT

الـ payload مقروء لأي أحد بـ atob. ليس مشفرًا!

الإصلاح: معرّف المستخدم ودوره فقط، وعمر قصير.

الجزء ٧ · الخلاصة

قائمة مراجعة لأي تطبيق فيه Auth

  1. access token قصير في الذاكرة (Zustand)، و refresh token في كوكي httpOnly + sameSite.
  2. interceptor يضيف Bearer، وآخر يلتقط 401 ← refresh واحد مشترك ← إعادة الطلب مرة واحدة.
  3. فشل الـ refresh = خروج محلي: امسح الـ store والكاش.
  4. حالة 'checking' عند فتح التطبيق، فلا وميض ولا redirect خاطئ.
  5. المستخدم من GET /me (React Query)، والتوكن في Zustand. لكل معلومة مصدر واحد.
  6. الـ guards للتجربة، والسيرفر هو من يقرر: 401 لـ "من أنت؟" و 403 لـ "غير مسموح".
